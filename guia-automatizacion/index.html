Three small automations that save you from boring emergencies

Expired certificates and unpatched known-exploited bugs are not exotic. They are things nobody was assigned to watch. Let a script watch them.

Scope: run these against domains and software you own or manage. The scripts only read public data (a TLS handshake on port 443, and a public CISA feed).

1. Certificate expiry alert (bash + OpenSSL)

This reads the certificate a server presents and exits with an error if it expires within N days (default 21). Save it as certcheck.sh:

#!/usr/bin/env bash
# Usage: ./certcheck.sh example.com [days]
set -u
host="${1:?usage: certcheck.sh host [days]}"
days="${2:-21}"
cert="$(echo | openssl s_client -servername "$host" -connect "$host:443" 2>/dev/null | openssl x509 2>/dev/null)"
if [ -z "$cert" ]; then echo "ERROR: could not read a certificate from $host:443"; exit 2; fi
expires="$(echo "$cert" | openssl x509 -noout -enddate | cut -d= -f2)"
if echo "$cert" | openssl x509 -noout -checkend $((days * 86400)) >/dev/null; then
  echo "OK: $host certificate valid for more than $days days (expires $expires)"
else
  echo "WARNING: $host certificate expires within $days days (expires $expires)"; exit 1
fi

Exit code 0 means fine, 1 means close to expiry, 2 means it could not read a certificate. Test it first against a domain of yours with a big number (./certcheck.sh yoursite.com 400) to see the warning path.

2. CISA KEV watcher (Node 18+)

CISA publishes the Known Exploited Vulnerabilities (KEV) catalog as a JSON feed. Each entry has fields such as cveID, vendorProject, product, dateAdded and dueDate. This script lists entries added in the last N days that match words from your stack. Save it as kev-watch.mjs:

// Usage: node kev-watch.mjs "fortinet,wordpress,apache" 7
const URL = "https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json";
const terms = (process.argv[2] || "").toLowerCase().split(",").map(s => s.trim()).filter(Boolean);
const days = Number(process.argv[3] || 7);
if (!terms.length) { console.error('usage: node kev-watch.mjs "vendor1,product2" [days]'); process.exit(2); }

const res = await fetch(URL);
if (!res.ok) { console.error("KEV feed error: HTTP " + res.status); process.exit(2); }
const { vulnerabilities } = await res.json();

const since = Date.now() - days * 86400_000;
const hits = vulnerabilities.filter(v =>
  Date.parse(v.dateAdded) >= since &&
  terms.some(t => `${v.vendorProject} ${v.product}`.toLowerCase().includes(t)));

for (const v of hits) {
  console.log(`${v.cveID}  ${v.vendorProject} ${v.product}  added ${v.dateAdded}  due ${v.dueDate}`);
  console.log(`  ${v.vulnerabilityName}`);
}
console.log(hits.length ? `${hits.length} match(es) in the last ${days} days.` : `No matches in the last ${days} days.`);
process.exit(hits.length ? 1 : 0);

It exits 1 when something matches, so a scheduler can treat it as a failure and make noise. Matching is a plain text search on vendor and product names, so use words that appear in them. The dueDate is the deadline CISA sets for US federal agencies; for you it is just a useful sense of urgency.

3. Run both on a schedule with GitHub Actions

Put the two scripts in a repository and add .github/workflows/watch.yml:

name: watch
on:
  schedule:
    - cron: "17 6 * * *"   # every day at 06:17 UTC
  workflow_dispatch:        # lets you run it by hand
jobs:
  certs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: bash certcheck.sh yoursite.com 21
  kev:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: node kev-watch.mjs "wordpress,apache,fortinet" 2

A failing job turns the run red. Things worth knowing from GitHub's documentation: scheduled workflows run on UTC time, the shortest interval is 5 minutes, runs can be delayed under heavy load, notifications for scheduled workflows go to the user who last modified the cron line, and in a public repository scheduled workflows are disabled automatically after 60 days without repository activity. That last one is the classic way an alert quietly dies, so put a calendar reminder on it or use the plain cron option below.

Plain cron alternative

17 6 * * * /opt/watch/certcheck.sh yoursite.com 21 || echo "cert warning" | mail -s "cert" you@yourdomain.com

Requires a working mail command on that machine. Without one, use the Actions route.

4. The same idea in n8n

As a recipe, not an exported flow: a Schedule Trigger (daily) feeds an HTTP Request node that GETs the KEV JSON URL above; a Code or Filter step keeps entries whose dateAdded is recent and whose vendorProject or product matches your list; an IF node checks that something is left; then a notification node (email, chat) sends the CVE ID and due date. Build it step by step and test with a wide time window first so you can see it fire.

Checklist

  • I list every domain whose certificate I am responsible for.
  • A scheduled job checks each one and fails loudly under 21 days.
  • I know which vendors and products I run, and the KEV watcher uses those names.
  • I tested both alerts by forcing a match, not just the quiet path.
  • Someone specific receives the alert and knows what to do with it.
  • I know how the schedule could silently stop (inactive repo, changed address).
