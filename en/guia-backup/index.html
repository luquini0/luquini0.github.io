Backing up your website: the basics you actually need

A backup you have never restored is a hope, not a backup. This guide covers the essentials in about 3 minutes.

The 3-2-1 rule

A classic, widely used rule: keep 3 copies of your data, on 2 different types of storage, with 1 copy off-site. If the server fails, the provider has a bad day or you make a mistake, there is always something to go back to.

What to back up on a website

  • Files: code, themes, plugins, images and anything users upload.
  • Database: content, users, orders, settings. Usually the most valuable part.
  • Email: if your mailboxes live on the same hosting, they need a copy too.
  • DNS: export or write down your records (A, CNAME, MX, TXT). Rebuilding them from memory is miserable.
  • Settings and credentials: kept in a password manager, not on the same server.

How often

The useful question is: how much work or how many sales can I afford to lose? A site that rarely changes can be backed up weekly; one with daily orders or content, daily or more often. Also take a manual copy before any big change (update, migration, redesign).

Test the restore on a clean environment

This is the step almost everyone skips. Every so often (say, once a quarter):

  1. Spin up an empty test environment (another host, a subdomain or a local machine).
  2. Restore files and database from the backup without touching the real site.
  3. Check that it opens, that you can log in, and that content and images are complete.
  4. Write down how long it took and which steps were missing from your documentation.

Off-server and immutable copies

A copy stored on the same server is lost together with it. Keep at least one with another provider or in another location. If possible, make it immutable: storage that does not allow the copy to be modified or deleted for a set period, which protects you from accidental deletion and ransomware. Many cloud storage services offer this; check your provider's documentation.

8-point checklist

  • I have 3 copies of my important data.
  • They use at least 2 different types of storage.
  • At least 1 copy is outside the server and the main provider.
  • I back up files and database (and email and DNS where it applies).
  • The frequency is based on what I can afford to lose.
  • There is an immutable or delete-protected copy.
  • I tested a full restore on a clean environment and it worked.
  • I know where the credentials are and who can restore if I am not around.
