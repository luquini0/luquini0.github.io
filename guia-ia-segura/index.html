Using AI at work without losing control

AI tools are useful and they are also software that reads untrusted text and sometimes has your permissions. Treat them accordingly.

1. Prompt injection: text can carry instructions

A model cannot reliably tell your instructions apart from instructions hidden in a web page, document, email or code comment it was asked to read. In the 2026 edition of the OWASP Top 10 for LLM Applications, prompt injection is still number one, and Excessive Agency (an LLM that can call tools, modify files or send email) climbed from sixth to third. Practical consequences:

  • Anything the model reads from outside (web, inbox, tickets, shared files) is untrusted input, even if it came through a tool you trust.
  • The more an assistant can do (send email, run commands, edit files), the more a planted instruction can cost you. Limit actions, not just prompts.
  • Require your confirmation for anything that sends data out, deletes, pays or changes permissions.
  • Do not rely on "ignore malicious instructions" in the system prompt as your only defense.

2. MCP servers and tool permissions

The Model Context Protocol lets an assistant call tools through servers you connect. Each server is code that runs with some access to your files, accounts or network.

  • Install only servers whose source and maintainer you can check, the same way you would vet a dependency.
  • Give each one the least access it needs: read-only where possible, a dedicated account or token instead of yours, a narrow folder instead of your whole disk.
  • Prefer approval prompts for write actions, and read them instead of clicking through.
  • Remove servers you stopped using.
  • Keep production credentials out of reach of an assistant that also reads untrusted content.

3. Reviewing generated code

  • Read it as you would read a stranger's pull request. If you cannot explain it, do not ship it.
  • Run it and run tests, ideally tests you wrote or reviewed yourself, in a throwaway environment first.
  • Check every dependency it adds: does the package exist, is it the one you meant (watch for look-alike names; models sometimes suggest package names that do not exist, and those names can repeat predictably), is it maintained?
  • Look hard at authentication, input handling, SQL and shell calls, file paths and anything that makes network requests.
  • Run your normal linters, dependency audit and secret scanner on it. Generated code gets no exemption.

4. Keys and secrets

  • Never paste API keys, passwords or customer data into a prompt unless your organization has approved that tool for that data.
  • Keep secrets in environment variables or a secrets manager, never in source files, and add the env file to .gitignore.
  • Turn on secret scanning in your code host. If a key leaks, rotate it first and clean the history afterwards: assume it is already copied.
  • Give assistants and automations their own keys with narrow scopes, so you can revoke one without breaking everything.

5. Data and accountability

  • Know where your prompts go and whether they are stored or used for training under your plan's terms.
  • Decide as a team which data is never allowed into external tools.
  • You stay accountable for the output. Verify facts, numbers and citations before they leave your desk.

Checklist

  • I treat everything an assistant reads from outside as untrusted.
  • Actions that send, delete, pay or change access need my confirmation.
  • Every MCP server is vetted, least-privilege and still in use.
  • I review generated code and its dependencies before merging.
  • No secrets in prompts, source files or history; secret scanning is on.
  • Assistants use dedicated, revocable keys.
  • My team has a written rule on what data may enter external tools.
